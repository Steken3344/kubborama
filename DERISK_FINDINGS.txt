## Verified API names (read from installed .d.ts — use these exactly)

Physics (@iwsdk/core):
  PhysicsBody      component — state: PhysicsState.Static|Dynamic|Kinematic,
                   linearDamping, angularDamping, gravityFactor (per body!)
  PhysicsShape     component — shape/collider definition (PhysicsShapeType)
  PhysicsManipulation  component — { force, linearVelocity, angularVelocity }
                   ONE-SHOT: applied once, then auto-removed from the entity.
  PhysicsSystem    system — global config includes gravity: Vec3.

Grab (@iwsdk/core):
  OneHandGrabbable, TwoHandsGrabbable, DistanceGrabbable, Grabbed (state
  component), GrabSystem, MovementMode.

Audio (@iwsdk/core):
  AudioSource, AudioSystem, AudioUtils, AudioInstance, AudioPool,
  PlaybackMode, DistanceModel (spatial audio built in, as planned).

## Design knots RESOLVED by the above

1. Throwing: on release, add PhysicsManipulation with the frame-averaged
   { linearVelocity, angularVelocity }. One-shot semantics fit a throw
   perfectly.
2. Wind: PhysicsManipulation is one-shot, so wind = re-add the component
   with the wind force EVERY TICK to sticks in Flying state (supported
   pattern), not a persistent force field. Cheap at our object count.
3. Variable gravity: two levers — PhysicsSystem global gravity (Vec3) for
   the world setting, and per-body gravityFactor for special effects.
4. Kubb pieces at rest: tune linearDamping/angularDamping on PhysicsBody
   to stop endless micro-wobble.

## IWSDK MCP tools — exact inventory (from Meta's official docs:
## developers.meta.com/horizon/documentation/iwsdk/ai/mcp-tools/)

32 tools in 9 categories. The ones that matter most to us, by name:
- Session: xr_get_session_status, xr_accept_session (simulates pressing
  "Enter XR"), xr_end_session.
- Transforms: xr_get_transform, xr_set_transform (meters, quat/Euler),
  xr_look_at, xr_animate_to (SMOOTH device motion over a duration).
- Input: xr_set_input_mode (controller/hands), xr_set_select_value
  (trigger/pinch values — supports grab-move-release), xr_select,
  xr_get_gamepad_state / xr_set_gamepad_state (controller-only).
- Browser: browser_screenshot (base64 PNG), browser_get_console_logs
  (pattern filtering), browser_reload_page.
- Scene: scene_get_hierarchy, scene_get_object_transform (incl.
  positionRelativeToXROrigin). Requires MCPRuntime (auto in IWSDK apps).
- ECS DEBUGGING SUITE (11 tools, requires MCPRuntime): ecs_pause,
  ecs_resume, ecs_step (advance N frames at FIXED timestep while paused),
  ecs_query_entity, ecs_find_entities, ecs_list_systems,
  ecs_list_components, ecs_toggle_system, ecs_set_component,
  ecs_snapshot (keeps 2), ecs_diff (compare snapshots).

TWO BIG CONSEQUENCES for our plan:

1. AUTOMATED THROW SIMULATION in the emulator — a scripted, repeatable
   full throw: xr_set_transform to place the hand at the swing start →
   xr_set_select_value to grip a stick → xr_animate_to to sweep the hand
   through an underhand arc → xr_set_select_value to release at a chosen
   point in the arc → ecs_find_entities/scene_get_object_transform to
   assert where the stick landed and what toppled. This makes the M2
   golden-throw regression fully scriptable inside the emulator, and lets
   Claude Code iterate on throw feel without a human for the mechanical
   part (Erik still owns FEEL judgments).
2. DETERMINISTIC PHYSICS DEBUGGING — ecs_pause + ecs_step (fixed timestep)
   + ecs_snapshot/ecs_diff = frame-by-frame inspection of a throw or a
   topple, with diffs showing exactly which components changed. Use this
   whenever a physics behavior is mysterious, and in the milestone review
   gate's adversarial pass.

Gotchas from the docs: ecs_step requires ecs_pause first; gamepad tools
don't work in hand-tracking mode; console logs exclude debug level by
default; Y = 1.6 m is standing eye height for positioning.

## The garden feeling is BUILT IN — don't hand-build any of this
## (verified by reading the installed @iwsdk/core typings)

Environment & lighting (@iwsdk/core environment/ + lighting/):
- DomeTexture component: equirectangular sky background from one file —
  { src (HDR/EXR/png/jpg/KTX2), intensity, rotation, blurriness }. Our
  Poly Haven HDRI sky = add ONE component with src pointing at the .hdr.
- IBLTexture component: image-based lighting from the same HDR (PMREM →
  scene.environment) — "the sun lights everything naturally" is ONE
  component; pair it with DomeTexture using the same file.
- DomeGradient / IBLGradient / GradientEnvironment: procedural sky
  gradient alternative (useful for a cheap dusk/dawn variant later).
- Declarative light components: DirectionalLightComponent (the sun),
  AmbientLightComponent, HemisphereLightComponent (sky/ground tint —
  nice over grass), plus Point/Spot/RectArea, all with LightShadowSpec/
  LightShadowMapSize options. Our "one directional sun" is a component,
  not custom code.

Ambient audio (@iwsdk/core audio/):
- AudioSource component has { loop, autoplay, positional, refDistance,
  rolloffFactor, maxDistance, distanceModel, volume }. Birdsong =
  an AudioSource with loop+autoplay. Bonus trick: make 2-3 POSITIONAL
  bird loops and place them IN the trees around the court — spatial
  audio then makes the garden feel alive as you turn your head, at
  near-zero cost. Background music = one NON-positional AudioSource
  (positional: false), matching the plan's stereo-atmosphere rule.

Also built in (relevant later):
- LevelSystem/LevelRoot + SceneJSON import: level/scene composition
  support (pairs with Meta Spatial Editor) — an alternative way to author
  environment scenes when we do themed arenas post-POC.
- AssetManager with manifest/caching and GLTF load transactions — use it
  for loading Kenney GLBs instead of raw three.js loaders.

Consequence for the plan: environment.ts in M1 shrinks to roughly:
one DomeTexture + one IBLTexture (same autumn_park HDR), one
DirectionalLightComponent for crisp sun shadows-lite, HemisphereLight for
grass tint, ground plane + court, Kenney props via AssetManager, and in
M5 two-three positional bird AudioSources in the trees + one non-
positional music source. Almost everything we planned to hand-build for
the outdoor feeling already ships as components.

## From Meta's IWSDK troubleshooting page (quick-reference checklist)

- "Enter XR" button missing → almost always: the app is not served over
  HTTPS (or sessionMode/browser mismatch). First thing to check when the
  headset shows the page but no VR entry.
- Hand tracking not working → must be enabled in World.create()/config XR
  features (ours already is).
- Generated assets missing → GLXF output belongs in /public/glxf; compiled
  UIKitML JSON belongs in /public/ui. If UI or level files "don't exist",
  the generation step didn't run — check before debugging code.
- ASSET OPTIMIZATION — adjusts our plan: the IWSDK vite plugin has its own
  asset-optimization pipeline that tracks dependencies (the repo also
  ships a GLTF-optimizer package). Meta's guidance: use "the plugin's
  dependency blocking rather than adding another copy" — i.e. do NOT
  bolt a parallel manual optimization pass onto assets the plugin already
  manages. Consequence: in M1, first INSPECT what the plugin already does
  to files in public/gltf & public/textures (build and diff output sizes);
  reach for manual gltf-transform/KTX2 only for gaps the plugin leaves.
  Our fetch-assets.sh still downloads raw sources — unchanged — but the
  optimize step may largely be free.

## Final API audit (read from installed typings) — 4 findings

1. NO public collision-event API. The physics typings expose no
   onCollision/contact callbacks (engine internals are private _engine*
   fields). DESIGN CHANGE: impact detection = a pure-core velocity-delta
   heuristic — track each piece's velocity per tick; |Δv| above a
   threshold = impact, with magnitude scaling sound volume + haptics.
   Cleaner for us anyway: fully unit-testable, no engine coupling.
   (Topple detection never needed collision events — unchanged.)
2. Grab system does NOT transfer velocity on release. The typings say it
   outright: "interactions should track grab/release events themselves".
   So the M2 throw-release design (frame-averaged hand velocity + lever-
   arm term + PhysicsManipulation) is REQUIRED, not optional. Confirmed
   as the right plan.
3. END GRIP is supported: grab Handles take targetPosOffset /
   targetQuatOffset (+ detachOnGrab, moveSpeedFactor) — the mechanism for
   holding the stick by its end exists; spike its exact option surface in
   M2. GOTCHA: DistanceGrabbable has returnToOrigin which snaps objects
   BACK when released — it must be OFF on sticks or every throw teleports
   home.
4. AudioUtils ships play(entity, fadeIn)/stop plus one-shot audio
   entities that auto-remove after playing — use these for the klonk
   variants instead of hand-rolled audio lifecycle code.
